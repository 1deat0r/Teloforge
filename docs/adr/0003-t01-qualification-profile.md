# ADR 0003: T01 qualification profile

- **Status:** Proposed profile revision 0.8; no runtime is authorized or qualified
- **Profile revision:** 0.8
- **Date:** 2026-09-28
- **Tracking:** [Issue #4](https://github.com/1deat0r/Teloforge/issues/4), milestone T01
- **Scope:** One finite Markdown-link repair ending in a draft pull request

This document proposes a concrete first runtime profile for T01. It is not an implementation or a qualification result. The approved r2 specification and [T01 task](../tasks/T01-intent-execution.md) remain the requirements. This profile may add detail but cannot weaken their authority, provenance, artifact-handoff, or recovery rules.

## Decision summary

Qualify one owner-authorized repair to one relative Markdown link in one tracked documentation file. Pin the target repository, base branch and commit, file, intent revision, action budget, and expiry before admission. The model may propose one patch. A deterministic validator checks the exact changed file and link target. The owner approves the canonical patch digest before any repository write. A constrained runner checks the immutable candidate snapshot without repository scripts or network access. The broker performs at most five create-only GitHub API writes: create one blob, one tree, one commit, one staging branch reference, then one draft PR in the target repository. The blob, tree, and commit are content-addressed objects; the branch reference must not already exist, and the PR must not already exist. No existing reference or PR may be updated. The owner must also approve a digest-bound repository automation profile. Revision 0.8 authorizes the initial read-only `Source CI` run caused by opening that draft PR; all other executable events are outside the grant. Its exact run and resource usage must be durably recorded before the task can reach `awaiting_pr_review`. The target base ref, staging ref, and relevant configuration must be frozen against non-owner actors for the write window. The authenticated owner/admin remains a trusted break-glass principal that GitHub cannot mechanically freeze. Any observed owner/admin intervention invalidates the active CI gate and is recorded as an out-of-band action; this profile does not claim to prevent or perfectly detect every owner/admin action. If the non-owner freeze, actor inventory, or trusted-owner boundary cannot be established, live GitHub writes stay disabled.

Use a direct OpenAI Responses API adapter in the trusted TypeScript process, one explicitly pinned model profile, PostgreSQL as the sole durable authority, and a Rust runner using a fail-closed Linux bubblewrap profile. Do not expose arbitrary shell, general HTTP, provider-hosted tools, or merge/deploy operations to the model or broker.

The split credential authority is preferred because GitHub's merge endpoint requires target-repository `Contents: write`. A staging-writer App receives that permission only on the staging repository. A distinct target-PR App receives `Pull requests: write` and the minimum read access needed to inspect the target and staging head, but no `Contents: write` on the target. The PR app installation topology and API calls must be qualified against the selected fork and actual repositories; do not assume an installation token can span separate installations or that documented endpoint permissions prove cross-fork access. If the split cannot be demonstrated, stop and return to the owner for a revised grant decision. A single-repository `Contents: write` token is weaker: the broker can withhold merge, but credential compromise could still merge. GitHub's create-PR endpoint takes a base branch name, not an expected base SHA, so the profile records and handles that race explicitly below rather than claiming an atomic SHA precondition.

## Pilot contract

### Target and task

The pilot task is one owner-selected broken relative link in one tracked Markdown file. The model receives only the owner's task statement, the selected file, a bounded repository path index, and any owner-approved neighboring documentation needed to identify the correct destination. It proposes a replacement destination that already exists at the pinned base commit. The deterministic checker verifies that the replacement resolves inside the target repository and that the changed link is syntactically valid.

The task must not be accepted until the owner selects the target repository and one genuine broken-link occurrence, and supplies an acceptance rubric for the intended destination. A read-only scan of the current editable Teloforge Markdown documents found no missing relative links; the historical review snapshots and approved bundle are not eligible pilot targets. Do not manufacture a production defect or silently switch to a different workload. A disposable fixture can validate mechanics but cannot count as the live repository-maintenance qualification.

At admission, bind all of the following:

- immutable target repository ID, staging repository ID, and base commit SHA;
- one allowlisted Markdown file path and the identified link occurrence;
- owner-authored intent revision, acceptance criteria, and exact action grant;
- requested model profile at admission, with provider-resolved response metadata attached to the immutable provider receipt when available; tool-schema version, checker version, runner image/runtime digest, and artifact policy;
- maximum input/output tokens, provider-call count, wall time, changed bytes, and expiry; reserve at most one downstream CI run of two GitHub-hosted jobs with 15-minute job timeouts (30 runner-minutes maximum), plus the owner-approved billing treatment;
- owner-approved, versioned provider data-use consent, repository automation profile digest, CI observation policy, and CI resource/billing profile;
- a reserved operation identity for each provider call and repository write, plus the immutable, versioned five-step GitHub operation-graph digest and the expected downstream CI observation identity/policy.

Bind both the target base branch name and its observed commit SHA. The current GitHub create-PR endpoint accepts a base branch name and does not expose an expected-base-SHA condition. Before any staging Git-object/ref create and immediately before PR creation, fetch the target ref and require the observed SHA to equal the admitted SHA. Before PR creation, also fetch the exact staging ref and require it to equal the approved commit SHA. The staging commit must be a child of the admitted base SHA. After PR creation, verify the returned base ref and SHA, staging head SHA, draft state, and canonical diff/metadata digest against the approval. If either ref drifts before a send claim, block without sending. GitHub does not atomically bind its PR create operation to either ref SHA or the automation-profile digest, so preflight and post-receipt reads alone cannot close these races. An independently enforced freeze must protect the target base ref, staging ref from creation onward, and relevant workflow/settings/integration configuration from all non-owner principals through the CI observation deadline. Qualification inventories collaborators, teams, installed Apps, and their effective permissions; no non-owner principal may retain write/triage access or Actions write, and the two T01 Apps must be scoped as specified. The target PR connector rejects PR close/reopen/update/delete, Actions dispatch/rerun/cancel, and any other unapproved method before network dispatch. GitHub does not provide a per-run lock against a trusted repository owner/admin; the owner/admin is therefore an explicit trusted break-glass principal, not a principal that the freeze claims to constrain. Any observed owner/admin run, cancellation, PR lifecycle mutation, permission/settings change, or workflow/configuration drift during the observation window is recorded as an out-of-band command that revokes the T01 gate, moves the task to `blocked_ci` or `blocked_automation_drift`, and requires fresh owner approval. The profile cannot prevent or guarantee detection of every owner/admin action, including a transient change that is reverted before it is observed; it does not defend against a malicious or unobservable trusted owner/admin. It is never treated as an authorized retry. Qualification must fault after staging-ref creation and show that detected staging-head drift prevents PR creation without another write or automatic compensation. If the non-owner freeze, actor inventory, or trusted-owner boundary cannot be established and disclosed, do not enable live branch or PR creation. If any drift is observed, preserve all receipts and require fresh owner review; never rebase, close, recreate, update, or compensate automatically.

The candidate must change exactly one existing regular Markdown file. It may alter only one link destination. Reject added/deleted files, any mode/type change, binary or non-UTF-8 content, symlinks, submodules, workflow/code/dependency/configuration changes, extra hunks, path traversal, and output exceeding the admitted byte limit. Require the target link to resolve to an existing file or directory at the pinned base. No unrelated broken links need to be repaired.

### Intent, grant, and approval

This first profile has one tenant and one preconfigured owner. Authentication must resolve to the owner's pre-bound immutable GitHub numeric user ID; display names, email matches, first-login-wins, or model assertions do not establish ownership. The owner revises the intent and grants the task's resource, actions, budgets, and expiry through the authenticated control API.

An exact-action approval is required after patch generation and before any GitHub write. It is bound to the target repository ID, staging repository ID, base SHA, canonical patch digest, changed path, expected blob/tree/commit digests (both Git object IDs and SHA-256 canonical-content digests), deterministic-check receipt, PR title/body digest, intent revision, grant digest, authorization epoch, ordered operation-graph digest, change-freeze evidence digest, CI observation policy and deadline rule, CI resource/billing reservation, and expiry. A changed patch, base SHA, grant, PR metadata, freeze evidence, CI profile/budget, or expired approval requires a new approval. The grant allows one create attempt for each of the expected blob, tree, commit, and staging branch reference, followed by one draft-PR create attempt. It authorizes no object or ref update, force-push, close, delete, merge, deployment, target-branch write, arbitrary issue/comment write, workflow dispatch, workflow rerun/cancellation, or repository administration. If the branch or PR already exists, stop and reconcile by read-only queries; do not overwrite or update it. Any changed patch requires a new intent approval and fresh unique object/reference/operation identities.

Before that approval, the work enters the owner-visible `awaiting_owner_approval` state. The approval view shows the full unified diff; target and staging repository IDs; base branch and pinned SHA; head SHA; deterministic-check receipt; patch, changed-path, PR-metadata, provider-consent, automation-profile, operation-graph, change-freeze evidence, CI-policy, and CI-billing digests; the exact ordered create-only external operations; reserved and maximum budgets; remaining expiry; and the base-ref/API limitation. It also explains in plain language that the new draft PR starts the pinned read-only `Source CI` workflow, names its two jobs and 15-minute per-job limits, shows the 30 runner-minute ceiling, whether usage is included or billable under the observed repository/plan, the owner-approved monetary ceiling or explicit unknown-cost treatment, the fixed observation window, and what an unexpected run or owner/admin intervention will do. The digest supplements this readable summary; it never replaces it. The authenticated owner can approve or reject the exact tuple. Rejection becomes a terminal `approval_rejected` execution state; expiry becomes `approval_expired`; revocation invalidates the pending approval and increments the authorization epoch. All three states are visibly non-executable. Approval is recorded as an immutable event and consumed once in the same transaction that admits the first external operation. Any material change requires a new approval.

OAuth is used only to establish the owner session. Use an exact HTTPS callback, one-use unpredictable `state`, PKCE S256, a short transaction lifetime, one-use authorization code handling, server-side identity lookup, secure opaque session cookies, CSRF checks on mutations, and session revocation. Do not use the OAuth token for repository effects. The GitHub App installations perform repository operations with short-lived installation tokens scoped to numeric repository IDs and minimum permissions.

### Model adapter and data boundary

The adapter calls the Responses API directly from the trusted TypeScript service. Use one owner-selected, exact model ID; `store: false`; foreground calls; no provider-hosted tools, remote MCP, browser, file-search, conversation, or background-mode features. Use a strict structured output schema and independently validate every response and tool request at runtime. Provider output is untrusted data. It cannot choose an operation, repository, path, authority, model, or credential.

Disable SDK-level retries (`maxRetries: 0`) so the durable operation state machine owns retry decisions. Persist a unique logical request identity, canonical request digest, budget reservation, and `dispatching` transition before sending. A lost response is an unknown outcome: retain its spend liability and record the request as uncertain. Do not assume provider-side idempotency or recover the model's hidden reasoning/session. Any explicit retry is a separately authorized attempt with a fresh reservation; unresolved earlier usage remains accounted as unknown.

Record requested model ID separately from resolved response metadata and capture provider-reported model/response identifiers and usage fields when present; a model alias does not pin hidden weights. Classify a request as `not_sent` only when failure occurs before the durable send claim and the adapter can prove no request left the process. After the durable send claim, a timeout, connection reset, worker loss, or missing response is `outcome_unknown` unless a provider receipt resolves it. Keep the maximum applicable liability reserved for unknown usage. Never infer a pre-send failure from a generic network error or automatically repeat a post-claim call.

Only bounded, owner-approved repository text crosses the provider boundary. Never include `.git`, environment files, credentials, secrets, private prompts, unrelated workspace data, or local machine paths. `store: false` is a request option and does not itself disable provider abuse-monitoring retention or other disclosed data controls. Before live qualification, the owner must approve an immutable, versioned `ProviderDataUseConsent` record containing provider and project identifiers, exact endpoint/model profile, purpose, permitted repository/content classes and byte limits, application-state setting, the actual project/organization retention mode as observed, known abuse-monitoring/retention behavior, local evidence retention, consent actor, creation time, expiry, and revocation state. Bind the consent digest to the intent revision, admission, and every provider operation. Before dispatch, confirm the consent is current and matches the resolved project/profile; show its summary in the exact-action approval view. Unknown or changed controls block provider dispatch. Use a dedicated provider project/key with the narrowest available response-creation permission, expiry/rotation, and provider-side spend/rate limits. Keep the key in a trusted secret store; never put it in the runner, candidate workspace, database row, outbox, source, or log.

### Runner and artifact boundary

The TypeScript kernel, authenticated API, PostgreSQL database, secret broker, and GitHub connector stay outside the candidate sandbox. The Rust runner accepts a versioned, runtime-validated command envelope; it does not parse a draft TypeScript type as proof of valid input. T01 exposes only typed operations for reading the admitted document, submitting one patch, and running the pinned link checker. It does not expose a general shell or execute repository scripts, package managers, hooks, filters, submodules, or LFS operations.

Host preflight on 2026-09-28: bubblewrap 0.11.1 launched a minimal trusted process with user/mount/network namespace isolation, and a transient user systemd scope enforced `memory.max=134217728`, `cpu.max=20000 100000`, and `pids.max=16`. The active AppArmor context remained `chatgpt (unconfined)`; the available profile list was not inspectable by this user, and no T01 seccomp policy was demonstrated. This is evidence for basic namespace launch and cgroup limits only. No untrusted repository or candidate code was run. This host remains unqualified until the selected profile proves enforceable AppArmor and seccomp policy, along with all remaining sandbox and cleanup requirements.

T01 supports only a local runner on the qualified host. The control process and runner supervisor use a permission-restricted Unix-domain socket, verify peer credentials, and bind every assignment to an authenticated runner identity, runner boot ID, one-use assignment capability, attempt ID, intent/grant digests, authorization epoch, lease generation, and runtime-profile digest. The capability is available only to the supervisor and is never inherited by candidate processes. One versioned JSON Schema is the protocol source; generate the TypeScript and Rust validators/types from it and bind each assignment to the schema digest. Negotiate an explicitly supported major/minor and schema digest before assignment; accept only enumerated compatible revisions, and reject an unknown version, schema digest, message kind, field, or limit. The assignment and outputs are typed operations, not commands or shell strings. T01's wire envelope is Teloforge-specific and does not claim Paperclip PRP wire compatibility. Use PRP's command/event/conformance concepts as design input, publish a field/semantic mapping and explicit incompatibilities, and reject PRP clients until a later revision passes shared compatibility fixtures.

The runner spool is a bounded SQLite delivery journal, never a task-state authority. Use one exclusive writer per registered runner, durable commits before transmission, explicit byte/record/age/per-attempt limits, and integrity checks on reopen. Keep the database outside every candidate mount. Every event has boot ID, attempt ID, lease generation, monotonically increasing sequence, stable event ID, and canonical payload digest. The kernel commits validated event/result, audit, and any resulting outbox transition before acknowledging that sequence. Reconnect replays unacknowledged records in order; identical duplicates return the committed result, while an identity/sequence with a different digest is rejected and quarantined. A runner never infers success from a local spool acknowledgement. At a spool or consumer limit, the controller applies explicit backpressure and stops candidate output; it never drops a record and then reports success. Heartbeats and cancellation are fenced by the same boot ID, lease generation, and authorization epoch. Protocol conformance evidence must include reconnect, lost acknowledgement, duplicate, conflict, stale assignment, overflow, corruption, and backpressure cases.

Reserve a protected, preallocated fixed-size failure marker outside the ordinary SQLite capacity for terminal transport faults. On `runner_spool_exhausted`, stop and reap the candidate cgroup, retain every unacknowledged row, and durably write the marker with boot/attempt/lease identity, the last known sequence, and the fault class. Send a classified failure when the control channel is available. If the marker write fails, make a best-effort direct fault report over the control channel; if that channel is unavailable too, heartbeat timeout must move the controller to `runner_recovery_required`, never expire the lease into reassignment. In either case, the local supervisor stays fail-stopped and exposes a distinct host-health fault; it cannot acknowledge completion, release the workspace, or start another attempt. Preserve all provider/effect reservations, and treat every send-claimed operation without a receipt as `outcome_unknown`. When communication returns, deliver any durable marker before ordinary replay. If no marker exists, use the PostgreSQL heartbeat-timeout transition, last acknowledged sequence, and operation IDs as the reconciliation starting point. Reconcile sequence gaps and send-claimed operations against PostgreSQL and their providers, and retain unknowns until resolved. On `runner_spool_corrupt`, quarantine the database without truncating or recreating it, preserve all recoverable rows, and record `runner_recovery_required` with the last controller-acknowledged sequence. Do not reassign the workspace or auto-resume until process cleanup is proven, all retained/missing history is reconciled, and a new lease generation is committed. If the marker itself cannot be durably written, the host-health fault must remain visible to the local operator and the controller-known lease remains fenced; never infer success, no effect, or zero-cost usage.

The durable control-plane fallback does not depend on the marker: when a registered runner misses its lease heartbeat, the controller atomically records `runner_recovery_required` in PostgreSQL with runner ID, boot ID, attempt ID, lease generation, last acknowledged sequence, expected missing interval, and all send-claimed operation IDs. It fences that runner, host, and resource and never expires the lease into a new assignment. Each controller process closes its local assignment/dispatch gate when PostgreSQL connectivity is lost. On startup and after every PostgreSQL connection-loss/reconnection cycle, the gate stays closed while the controller obtains the shared recovery lock and sweeps all nonterminal attempts and active runner registrations for missed heartbeats. In one transaction it persists `runner_recovery_required` and fences each affected runner, host, and resource before marking that recovery epoch complete. Assignment admission and runner boot registration serialize against that durable recovery epoch; no scheduler or dispatcher may use a local readiness cache to bypass it. If PostgreSQL is unavailable, the sweep or barrier commit fails, or the durable epoch cannot be verified, that process keeps assignment closed. This applies even when the controller process did not restart during the outage. Reconnection permits evidence replay and reconciliation, not a new assignment from that process, until the sweep commits. Recovery requires an authorized operator to quarantine and inspect the host, prove process and writable-descriptor cleanup, preserve or recover the spool and marker if available, reconcile missing sequences and classify every uncertain provider/GitHub operation as applied, not applied, or still unknown, and record the evidence and operator decision in PostgreSQL. Only then may the controller commit a new lease generation and runner boot registration. If any proof is missing, the resource remains fenced; no marker is required to discover or retain this recovery state.

The host profile is Linux x86_64 with a pinned bubblewrap/runtime/checker profile. `bwrap` availability alone does not qualify the boundary. Before launch, prove the exact unprivileged namespace, AppArmor, seccomp, cgroup-v2 resource-control, mount, environment, inherited-file-descriptor, and process-tree cleanup invariants on the target host. Candidate execution has no network, host home, host runtime sockets, provider/GitHub token, Docker socket, SSH material, or writable host path. The assigned workspace is the only writable mount. Do not fall back to host execution when any invariant is unavailable.

On candidate termination, kill and reconcile the complete process cgroup, prove no process or writable descriptor remains, then freeze an immutable snapshot. A separate unprivileged collector opens only declared regular files beneath the snapshot using descriptor-rooted, no-follow, no-cross-device resolution. Require link count one, bounded path/file/count/total-byte limits, hash bytes from the same file descriptor used to copy, and quarantine the artifact if any proof is missing. Finalized artifacts retain tenant, repository, base-SHA, intent, attempt, tool/checker version, and source provenance. Artifact failure prevents dependent task completion.

### GitHub effect boundary

Use two GitHub Apps with separate installation and key custody:

1. **Staging writer App:** installed only on the staging repository with `Contents: write` and no target-repository installation. Its fixed REST operation set creates the exact approved blob, tree, commit, and one previously nonexistent uniquely named staging reference from the admitted base commit. Each object/reference has its own stable operation ID, expected digest, reservation, audit record, and outbox/send-claim transition. It never updates or force-pushes a branch. Reconcile ambiguous object writes only by reading the expected object SHA and verifying its canonical content; reconcile an ambiguous ref create by reading that exact ref. Missing or conflicting evidence stays unknown and is never resolved with another create request. Its token has no target-repository authority.
2. **Target PR App:** installed on the target and staging repositories so it can inspect the head and base. Grant `Contents: read`, `Pull requests: write`, and `Actions: read`, but no `Contents: write`, administration, actions/workflows write, secrets, deployments, or members permission. Its broker interface may issue one create-draft-PR request from the staging head to the exact pinned target base, then read the one expected workflow run and its jobs. Subscribe to the required `pull_request`, `workflow_run`, `push`, `create`, and `delete` webhook events; authenticate webhook signatures, deduplicate delivery IDs, and persist every relevant delivery before acknowledging it. Ref events are used to invalidate the gate if the pinned target base or approved staging ref changes during the write/observation window. It never updates, closes, reopens, recreates a PR, reruns/cancels a workflow, dispatches a workflow, or writes checks. If a PR with the operation identity exists, verify it by read-only queries and stop. Its token is scoped to the two fixed repository IDs and cannot push content or use the merge endpoint on either repository, which requires `Contents: write` on the base repository. GitHub's broad `Pull requests: write` permission still permits lifecycle operations outside this connector; treat that capability as a residual token-compromise risk and include it in the owner approval.

GitHub's permission tiers are broader than these endpoint allowlists: `Contents: write` can modify other staging content and refs, and `Pull requests: write` can update or close PRs. The App permissions limit repository reach, while the trusted connector enforces the operation set. Keep private keys outside the application process, mint short-lived installation tokens only for a send window, and never expose tokens to the runner, model, workspace, or logs. This does not eliminate the broader authority of a stolen short-lived token or compromised connector; disclose that residual in the owner approval and qualification record.

The connector uses typed, constant endpoint/method templates and numeric repository/installation IDs. It does not accept arbitrary URLs, methods, GraphQL documents, or caller-supplied repository names. A deterministic branch name includes the work/operation identity. PR metadata contains an opaque operation marker, base/head SHA, task summary, changed path, check receipt, and budget summary; it contains no private prompt or host path.

Before each create effect, commit the exact operation ID, canonical-arguments digest, current grant and authorization epoch, budget reservation, lease generation, freeze-evidence digest, audit entry, and outbox row in one PostgreSQL transaction. Recheck authority and freeze validity at a fenced send claim immediately before dispatch. Each blob, tree, commit, reference, or PR create operation has one send attempt only. After an ambiguous write, query only the exact object/ref/PR identity using read-only operations and verify its expected digest and provenance. If evidence is absent, conflicting, or unavailable, preserve `outcome_unknown` for human reconciliation; do not issue another create request. Orphaned prepared Git objects remain inert and are not automatically deleted. A subsequent owner-approved intent may use new operation identities and a unique branch after the previous outcome is resolved; it may reuse an existing content-addressed object only after a read-only query verifies its exact canonical content and provenance.

Persist the complete GitHub write batch and ordered dependency graph in PostgreSQL: `blob → tree → commit → staging_ref → draft_pr`. Each operation has one of these durable states: `pending`, `ready`, `send_claimed`, `applied`, `not_applied`, `outcome_unknown`, or `blocked`. The next operation becomes `ready` only when its predecessor is verified `applied`, the current grant is valid, and the owner-approved freeze remains valid; a known non-effect, unknown, or blocked predecessor never enables a successor. In one transaction, record a verified receipt, settle its known accounting, write its audit result, and enqueue the successor; keep the HTTP request outside the transaction. Do not expose or claim a successor while its predecessor is `send_claimed`, `outcome_unknown`, `not_applied`, or otherwise unresolved. Before every successor send claim, recheck the current authorization epoch, lease generation, change-freeze evidence, and exact expected object/ref SHA. In particular, PR creation requires applied receipts for the blob, tree, commit, and staging ref plus fresh matching target-base and staging-ref reads. A pause stops unclaimed successors. Revocation, drift, freeze loss, cancellation, budget exhaustion, or other terminal stop blocks every unclaimed successor with a durable reason and requires a fresh exact-action approval before any later attempt. Reconcile every send-claimed operation to `applied`, `not_applied`, or `outcome_unknown`; if no trustworthy evidence can distinguish an applied effect from no effect, retain `outcome_unknown`. A stopped batch is never continued to satisfy successful completion. Successful completion requires every authorized direct operation to be known applied. A separate failed or cancelled execution outcome may be finalized once every send-claimed operation has a durable classification and every unclaimed successor is durably blocked; this records a terminal stop, not success. Any `outcome_unknown` remains an independent reconciliation obligation with its effect/budget reservation retained, and blocks a new attempt that could repeat or depend on that effect until read-only reconciliation resolves it. Do not automatically compensate applied partial writes. Late reconciliation may update the operation liability and owner-visible status idempotently, but cannot reopen the stopped attempt or reactivate its successors.

The staging branch and target draft PR remain after completion. Closing/deleting them is a separate external effect and is not automatic compensation. The target repository's current PR rules must require the human-maintainer path and current CI before merge; the Teloforge app and broker have no merge operation. The owner must confirm target repository policy before qualification.

Treat both branch creation and draft-PR creation as triggers for further GitHub effects. Revision 0.8 permits one initial downstream executable run attributable to this grant: the target repository's `Source CI` workflow with ID `368849222`, pinned to `.github/workflows/ci.yml` SHA-256 `67ced510a4e55fc5e1cf8d8eef2422e9dabf335596f025185097e3f3e52baa45` (the file digest is rechecked before the first write and before PR creation). Its observed definition has workflow-level `contents: read`, a `pull_request` trigger with GitHub's default `opened`, `synchronize`, and `reopened` activity types, `push` to `main`, `workflow_dispatch`, and `cancel-in-progress: true`; it has two jobs (`TypeScript` and `Rust`) each with a 15-minute timeout, does not reference `secrets.*`, does not use `pull_request_target`, and pins third-party actions by full commit SHA. The only run authorized as a T01 consequence is the initial run correlated with the new PR's `opened` event. This profile preserves the existing `synchronize` CI required for subsequent project development; T01 itself never updates or reopens the PR, dispatches, reruns, or cancels Actions.

Before the draft-PR send claim, persist `ci_observation_start_at` as the send-claim timestamp and `ci_observation_deadline_at = ci_observation_start_at + 30 minutes` in the exact-action approval/operation record; do not extend either timestamp after seeing a run. This window is the maximum owner-approved interval and is bound to the PR operation before the HTTP request leaves the process. The exact match predicate requires all of: workflow ID and file digest equal the admitted profile; target numeric repository ID equal the admitted target; one PR number equal the newly created PR receipt; `run.event=pull_request`; the run's associated head/base repository IDs, refs, and SHAs equal the approved staging head and admitted target base; its observed pull-request webhook is `action=opened`; `run_attempt=1`; run start and completion occur by the fixed deadline; the overall conclusion is `success`; and the complete expected job set is exactly `TypeScript` and `Rust`, both `success`. Lookup scope is fixed to that target repository, workflow ID, PR number, head SHA, and observation interval; each signed `workflow_run` webhook triggers only a read of its run/jobs, and one final paginated run lookup occurs at the deadline. At the deadline, also read the exact target base and staging refs and require their SHAs to remain equal to the admitted base and approved staging head; a relevant authenticated `push`, `create`, or `delete` event during the window blocks even if a later read matches. There is no unbounded polling or search outside that tuple and the two exact refs. The final database decision occurs at the immutable deadline; an earlier anomaly can only block, never pass early. Correlate signed `pull_request`, `workflow_run`, and relevant ref-event webhook receipts by delivery ID. Zero, duplicate, unmatched, late, cancelled, failed, or ambiguous runs are `blocked_ci`.

The expected run reserves at most 30 GitHub-hosted runner-minutes (two jobs × 15-minute timeout); record each job's observed duration and billing treatment. For a public repository on standard GitHub-hosted runners, require the profile to confirm the current included/free treatment; for any other visibility or runner class, reserve the owner-approved account-plan cost ceiling before PR creation. If the billing ledger or job usage is unavailable, retain the corresponding maximum/unknown liability and do not report zero spend. The owner-visible approval and final receipt show these resource units and monetary treatment.

GitHub does not provide a setting that prevents a trusted owner/admin from rerunning or cancelling a workflow, closing/reopening the PR, or dispatching the workflow while Actions remain enabled. The target PR App has no Actions write permission, GitHub rejects its rerun/cancel calls, and connector conformance rejects PR lifecycle methods. The trusted owner/admin can still intervene; this profile cannot prevent or guarantee detection of every owner/admin action, especially a transient configuration change that is reverted before it is observed. Any observed PR, workflow-run, or relevant ref event, or any failed final ref check, invalidates the prior CI handoff, records available actor/run/usage evidence, and transitions to `blocked_ci`. Do not claim an all-actor freeze or fold such usage into the T01 grant. T01 is not designed to resist a malicious or unobservable repository owner/admin, and cannot be qualified if the owner cannot accept this trust boundary.

The staging repository must have Actions disabled and no event-reactive webhook or installed integration may execute on the staging ref. The owner-approved automation profile enumerates the target and staging workflow inventories, workflow digests and event filters, Actions enablement and permission settings, relevant webhooks and installed integrations, deployments, organization-level secrets, actor inventory, billing profile, and the expected notification audience. The current repository also lists a GitHub-managed `Dependabot Updates` workflow; it is outside the permitted T01 effect and must be inventoried and shown not to be triggered by the selected documentation-only PR or to mutate the frozen refs during the write window. Unknown or uninspectable event-reactive integrations block live writes unless the owner supplies complete attestation and the non-owner freeze proves they cannot run. GitHub's native subscriber/participant notifications may still be sent; the approval discloses this possible audience, and notification delivery is a non-gating informational consequence that cannot execute code or create another effect.

The final pre-write check revalidates the workflow tree/revision and every inspectable setting, but these reads are not an atomic lock. The non-owner freeze covers the target base ref, staging ref from creation onward, and relevant workflow, repository/organization setting, webhook, integration, secret, and notification changes through the CI observation deadline. Qualification must attempt competing target-base and staging-ref updates (including an update using the staging App), along with non-owner profile changes during this interval, and demonstrate the freeze denies them. The profile must test missing, stale, revoked, or interrupted freeze evidence; no create request may be sent. The trusted owner/admin exception is not mechanically blocked and cannot be perfectly monitored: any observed out-of-band owner/admin PR lifecycle, Actions, ref, permission, or settings change revokes the CI gate. This profile trusts the owner/admin and does not defend against that principal. If the non-owner freeze, exact automation profile, or owner/admin trust boundary cannot be demonstrated and disclosed, keep live GitHub writes disabled. The exact branch and draft-PR creates, the one authorized initial `Source CI` run, its reserved usage, and possible native notifications are included in the owner's grant. App permissions alone do not constrain triggered workflows, webhooks, or other integrations.

### Operator lifecycle

- **Pause:** one transaction disables new admissions and future sends. An already claimed external operation proceeds to reconciliation; pause does not claim to undo it.
- **Cancel requested:** first revoke future authority and increment the authorization epoch, then request runner/process cancellation. Keep budget reservations and uncertain provider liability until they are reconciled.
- **Cancel confirmed:** means execution is stopped, not that every remote effect was absent or reversed. Confirm only after process-tree cleanup, all send-claimed operations have durable `applied`, `not_applied`, or `outcome_unknown` classifications, and all unclaimed successors are durably blocked. Preserve completed branch/PR effects; any cleanup requires separate approval. Keep unresolved external outcomes and reservations visibly open; they block related new sends until read-only reconciliation resolves them.
- **Stopped with unresolved effects:** execution is terminally failed or cancelled, every unclaimed successor is blocked, and the cleaned runner lease may be released; list each unresolved operation, possible partial effect, retained reservation, and read-only reconciliation step. This is not successful completion and does not authorize a replacement send.
- **Blocked:** name the unmet prerequisite, affected operation/resource, evidence available, and owner action needed.
- **Outcome unknown:** name the stable operation ID, possible external effect, spend liability, and reconciliation query/result. This obligation can remain open after the execution is stopped and its clean runner lease is released. Do not offer a blind retry or permit a dependent/repeating send.
- **Awaiting owner approval:** show the immutable action tuple and consent/risk summaries above; only the authenticated owner can approve, reject, or revoke it.
- **Approval rejected / expired:** remain visibly non-executable; a new attempt requires a new owner command and current authority.
- **Blocked on base drift:** preserve the actual PR receipt if one exists, identify both observed base SHAs, and wait for a new owner decision; never amend the PR automatically.
- **Blocked on staging drift:** preserve object/ref/PR receipts, identify the approved and observed staging head SHAs, prevent PR creation if the drift precedes that send claim, and require owner review without updating, recreating, or compensating automatically.
- **Transport blocked / runner recovery required:** show the typed spool failure, boot/attempt/lease identity, last controller-acknowledged sequence, retained or missing event interval, outstanding reservations, and required reconciliation. The PostgreSQL heartbeat-timeout record survives controller restart and is the recovery source if marker and channel both fail. Require an authorized operator recovery ceremony and keep the lease fenced; do not offer automatic resume while history or cleanup is uncertain.
- **Awaiting CI:** the PR receipt is verified and one matching run is being observed within its fixed window; execution cannot be handed to a reviewer yet.
- **Blocked CI:** a run is absent, duplicate, mismatched, late, failed, cancelled, rerun, or altered by an out-of-band PR/Actions event; show the exact webhook/run receipt, usage liability, actor, and owner decision needed. Teloforge never reruns, dispatches, cancels, or reopens it.
- **Awaiting PR review:** execution, artifact, deterministic-check, PR, and CI evidence are durably recorded and the initial run passed within its fixed window; the maintenance outcome remains pending human review/merge. Any later associated run or PR lifecycle event invalidates this handoff and returns the task to `blocked_ci`.

Cancellation request, runner termination, external-effect reconciliation, and confirmed cancellation are distinct events. Stale lease generations and authorization epochs cannot commit results or authorize later effects.

## Authority and persistence invariants

The following state is authoritative only in PostgreSQL: owner/session binding, intent and revision, grant and authorization epoch, budget reservations and accounting, work/attempt identity, resource lease and generation, external-operation identities and receipts, artifact metadata, audit, outbox, and materialized operator state. Runner spool data is an event-delivery aid; it is never an alternate authority.

Admission validates the authenticated principal, request schema, current intent revision, grant, profile, budget, exclusivity, expiry, and provenance before domain admission. One database transaction persists the admission binding, reservation, resource lease, command result, audit record, and outbox entry. The dispatcher claims from this durable outbox; it does not hold a database transaction open across a provider or GitHub request.

Idempotency keys bind to canonical arguments and expected revisions. Replaying the same identity/payload returns the stored result; reusing an identity with a different payload is rejected. Events are deduplicated by stable source/attempt/sequence identity plus payload digest. A stale runner boot ID, lease generation, authorization epoch, or intent revision cannot finalize state.

## Bounded maintained-intent triggers

T01 implements two explicit trigger classes, but only `manual_once` is enabled for the live pilot. A finite intent accepts one authenticated owner start and admits at most one attempt. A maintained intent may be represented only with a declared wake source, immutable trigger-policy revision, minimum interval, maximum runs per window, maximum total runs, maximum consecutive no-progress outcomes, wall-clock expiry, total and per-attempt budget ceilings, stop conditions, and an explicit owner grant. Each wake is a bounded, versioned trigger receipt with a stable source/event identity, observed time, intent revision, and payload digest; it cannot directly execute an action. The kernel deduplicates trigger receipts, evaluates the current policy/authority and budget, then separately admits work. Out-of-window, duplicate, stale-revision, paused, revoked, expired, over-limit, or over-budget triggers are recorded as rejected with a reason. No catch-up burst is allowed after downtime. There is at most one active attempt per exclusive resource. An unresolved provider or repository effect, repeated no-progress boundary, runner-loss ambiguity, or exhausted budget pauses further automatic wakes pending owner action. T01 acceptance exercises these rules with a deterministic synthetic event source; it does not install a recurring schedule or enable maintained execution for the live pilot.

## Atomic finalization

Artifact bytes are first copied into immutable, content-addressed storage and verified by the isolated collector; they are not authoritative until PostgreSQL records the finalization transaction. The kernel rechecks that the attempt remains bound to its admitted intent revision and grant, the current control-plane stop transition and authorization epoch, runner boot ID, lease generation, and every stable operation identity. A failed/cancelled stop is finalized by the trusted kernel against its current stop command, never by a stale runner event; if the intent was superseded, record the stop against the historical admitted revision and do not inherit authority from the newer revision. The finalization transaction binds the artifact/snapshot digest and collector receipt or an explicit withheld/quarantined disposition, deterministic-check receipt, provider request/usage state (known or explicitly unknown liability), each GitHub blob/tree/commit/ref/PR receipt state (`applied`, `not_applied`, `outcome_unknown`, or `blocked`), the approved CI-profile digest and fixed observation start/deadline, the authenticated PR-opened/workflow-run delivery IDs, every associated run/attempt/job conclusion, observed runner-minutes and billing treatment (known or explicitly unknown liability), any out-of-band owner/admin actor/event, command result, final budget settlement and retained reservations, terminal execution outcome/reason, audit event, outbox events, operator state, qualification-case result/cohort accounting, and transition revision. After the verified PR receipt, persist `awaiting_ci` and its pre-reserved run identity/window before observing the workflow. A single transaction records each authenticated CI observation and audit receipt; only one exact matching run with all expected jobs successful by the fixed deadline, no conflicting attempt/event, and complete usage accounting may transition to `awaiting_pr_review`. Failure, absence at the deadline, duplicate/mismatched/late runs, or a privileged out-of-band intervention durably enters `blocked_ci` and cannot be reported as success. A later authenticated PR-lifecycle or workflow-run event that changes that receipt invalidates the handoff in a new transaction and returns the task to `blocked_ci`. Successful completion is allowed only when all authorized direct operations are verified applied and required artifact, checker, provider, PR, and CI conditions hold. A failed/cancelled stop is also atomically recordable after each send-claimed effect has a durable outcome classification and every unclaimed successor is blocked; it must not be dropped from the frozen qualification cohort or reported as successful. Unknown outcomes retain their reservations and visible reconciliation obligations.

The resource lease is released only after the runner supervisor proves the full process cgroup is empty, writable descriptors are gone, and the immutable snapshot is sealed or its withholding/quarantine is durably recorded. If cleanup proof is absent, keep the lease fenced and expose `blocked_cleanup`. An external `outcome_unknown` alone does not retain a cleaned runner/workspace lease: retain its effect and budget reservations separately, keep the execution visibly stopped with unresolved effects, and block any related/repeating sends until read-only reconciliation resolves it. Do not release the resource lease or admit a conflicting workspace assignment before runner cleanup and event-history reconciliation. Enter `awaiting_pr_review` only after artifact/checker evidence is finalized, every external write is known, the approved draft PR receipt matches the admitted head and metadata, the one matching initial CI run and all its jobs have passed within the immutable observation window, usage and billing are accounted (or an explicit permitted unknown liability is retained), and no active runner or lease remains. Continue accepting authenticated `pull_request` and `workflow_run` events for the handed-off PR; any later PR lifecycle change, run attempt, cancellation, or conclusion change invalidates the handoff and moves it to `blocked_ci`. Human review/merge remains outside this finalization contract.

The qualification record includes a versioned case manifest with case ID, invariant, fixture/data digest, expected evidence, exact source/profile/host revision, and pre-registered repetition count where repetition is meaningful. Freeze the manifest before execution, store its digest, and bind every result to that digest. Each case is reported as `pass`, `fail`, `skipped`, or `inconclusive`, with observed count, denominator, and a reason for missing evidence; aggregate pass rates never hide skipped or inconclusive cases. Mandatory safety/fail-stop cases, including marker-write and control-channel failures, cannot be marked skipped. If they cannot be safely exercised, report `inconclusive` and leave the qualification gate unmet. A faulted attempt cannot be recorded as success or as zero-cost merely because its marker or transport failed; unresolved provider/effect reservations remain visible. The semantic repair verdict (the selected destination satisfies the owner-authored rubric and deterministic path checks) is recorded separately from authorization and policy decisions, and includes the owner rubric digest and identity of the authorized assessor. A semantic pass cannot create authority, and an authorized action cannot be reported as a correct repair without semantic evidence.

## Rejected shortcuts and limits

- **Authenticated coding CLI session as model adapter:** rejected for T01. It is not a dedicated provider API profile with explicit cost, retry, storage, and operation accounting.
- **General-purpose shell or repository scripts:** rejected. The selected task is expressible through a narrow document read/patch/check contract.
- **One target-repository Contents-write token with a claim that it cannot merge:** rejected. The broker can deny merge, but the token itself can merge.
- **Background provider calls with `store: false`:** excluded from this profile until their data-retention behavior and reconciliation value are explicitly accepted.
- **Automatic cancellation cleanup or blind retry:** rejected because a completed/unknown external write cannot be safely treated as absent.
- **Unqualified bwrap host fallback:** rejected. Failure to establish the target profile leaves the capability disabled.
- **Treating GitHub PR creation as a harmless metadata call:** rejected. It may trigger workflows, webhooks, integrations, and notifications, which must be disclosed and included in the owner grant.
- **Claiming the PR targets an immutable branch SHA:** rejected. The endpoint accepts a branch name; the bounded preflight/post-receipt and base-drift stop state are required.
